# ProtoDock 多端产品工作区与团队协作契约

仅在以下任务中读取本文件：创建或迁移多端产品工作区、设计跨端需求、整理共享 PRD、协调产品/设计/前端/后端交付、发布同一产品的多个端。普通单端页面修改无需加载。

## 1. 第一原则

一个产品只有一套共享业务事实，但可以有多个独立可运行的端。

- 共享事实只写在 `shared-docs/`。
- 页面行为只写在所属端的 `docs/<page-id>.md`。
- 每个端保留完整项目和完整 Canvas。
- 工作区只负责产品身份、端切换、共享文档和发布快照。
- 不建立第二套功能数据库、跨端 Canvas、同步服务或文档复制机制。

## 2. 新版标准目录

```text
product-workspace/
├── protodock.workspace.json             # 必需：产品身份、统一版本、端列表
├── README.md                            # 必需：团队开工入口
├── .gitignore                           # 必需：临时层排除规则
├── shared-docs/                         # 必需：直属 Markdown，共享事实来源
│   ├── 01-product-overview.md
│   ├── 02-roles-permissions.md
│   ├── 03-domain-data-contract.md
│   ├── 04-interface-event-contract.md
│   ├── 05-cross-end-flows.md
│   └── 90-decisions-open-questions.md
├── prototypes/
│   ├── parent/
│   │   ├── protodock.project.json
│   │   ├── README.md
│   │   ├── pages/
│   │   ├── docs/
│   │   ├── assets/                      # 可选
│   │   ├── source/                      # 可选，或一个原生 src/app/miniprogram 根
│   │   ├── scripts/                     # 可选
│   │   ├── tests/                       # 可选
│   │   ├── qa/                          # 可选
│   │   └── protodock/backups/
│   ├── teacher/
│   └── admin/
├── references/                          # 可选：跨端有效参考
├── qa/                                  # 可选：跨端验收证据
├── scripts/                             # 可选：跨端构建/验证编排
├── tests/                               # 可选：跨端自动化验收
├── protodock/backups/                   # 本地工作区清单备份
└── temps/                               # 本地临时层，必须忽略
```

目录边界：

- **协作层**：根 README 与 `shared-docs/`，由团队共同维护。
- **端项目层**：每个 `prototypes/<endpoint>/` 均是旧版兼容的完整 ProtoDock 项目。
- **工作层**：源码、脚本、测试、有效参考和当前 QA 证据，保留在 Git 中但不进入发布 ZIP。
- **临时层**：`temps/`、备份、本地密钥、缓存、日志和发布 ZIP，不进入 Git、Share 或发布包。

禁止在根或子端创建 `dist/`、`build/`、完整交付副本、嵌套 ProtoDock 项目或第二份可编辑源。发布 ZIP 必须在项目外或系统临时目录生成。

新建时从 Skill 的 `templates/product-workspace/` 复制工作区清单、README、`.gitignore` 和共享文档骨架，再替换真实产品信息。模板中的空章节是创建输入，不是可发布内容；交付前必须填写并通过校验。

## 3. Git 所有权

- 新建独立产品时，工作区根目录就是该产品的唯一 Git 根。
- 产品已经位于同一产品 monorepo 时，保留现有上层仓库作为唯一 Git 根；工作区根仍是 ProtoDock 的产品源码边界，但不重复初始化 `.git`。
- 子端不得再包含 `.git`；跨端改动必须能在一个分支和一个 diff 中审查。
- 功能分支命名 `feat/<product>-<feature>`，验收后合并到长期产品分支 `project/<product>` 并删除。
- 正式版本使用不可变标签 `release/<product>/<version>`，不为每个版本创建长期孤立分支。
- 同一跨端需求的共享文档、受影响页面 PRD、页面产物、Canvas 增量和 `pendingChanges` 必须在同一提交范围内。
- 已有独立仓库可以继续打开；迁移时先设计历史合并和责任边界，不删除 `.git`、不搬文件、不重写历史，直到用户明确批准。
- 迁移分支必须从目标唯一 Git 根创建。旧目录保持只读，新工作区写入新目录；验收和确认合并前不得覆盖、删除或重命名旧目录。

## 4. 共享文档权威

### `01-product-overview.md`

必需章节：`产品目标`、`用户与使用场景`、`产品边界`、`端与职责`、`成功标准`。

回答产品为何存在、每个端负责什么、不负责什么，以及什么结果才算成功。不要写页面清单或实现文件。

### `02-roles-permissions.md`

必需章节：`角色定义`、`权限矩阵`、`数据范围`、`越权处理`。

权限矩阵至少区分查看、创建、编辑、审批/发布、删除/撤回和管理能力。前端隐藏入口不代替后端权限校验。

### `03-domain-data-contract.md`

必需章节：`术语`、`核心实体`、`字段与口径`、`状态机`、`数据归属与来源`、`一致性与生命周期`。

每个关键实体说明标识、核心字段、枚举、空值、时间口径、事实来源、状态迁移、删除/失效规则和跨端一致性。不要伪造数据库表结构；未确认字段进入决策文档。

### `04-interface-event-contract.md`

必需章节：`前端职责`、`后端职责`、`接口契约`、`错误与重试`、`幂等与并发`、`权限与审计`、`联调数据`。

接口契约以业务能力为单位，写明调用方、触发条件、输入语义、成功结果、错误语义和状态影响。只有接口已经确定时才写具体 URL/字段；否则写业务契约并标记负责人，不自行发明。

### `05-cross-end-flows.md`

必需章节：`流程索引`、`主流程`、`状态与事件`、`异常与补偿`、`跨端验收`。

每个流程使用稳定标识，例如 `FLOW-REPORT-PUBLISH`，并包含：目标、参与端和角色、前置、编号主流程、状态/事件、失败恢复、受影响页面 ID、依赖接口以及端到端验收。

### `90-decisions-open-questions.md`

必需章节：`已确认决策`、`待确认问题`、`变更记录`。

每个待确认项写负责人、影响范围和期望确认时间。未决策内容不得伪装成页面 UI、接口字段或后端规则。

## 5. 页面 PRD 与共享契约

工作区内每个页面 PRD 在一级标题后增加：

```md
## 关联共享契约

- 共享契约：`03-domain-data-contract`、`04-interface-event-contract`、`05-cross-end-flows` 中的 `FLOW-REPORT-PUBLISH`。
- 本页职责：展示本班级周报状态并发起发布。
- 依赖能力：周报查询、发布权限、幂等发布和状态刷新。
```

若页面确实没有跨端依赖：

```md
- 共享契约：无（端内独立流程）。
- 本页职责：仅切换当前页面的本地展示模式。
- 依赖能力：无服务端能力。
```

页面 PRD 继续写页面定位、使用场景、前置条件、页面内容、交互规则、业务规则、状态与异常、数据影响、产品验收、非本期范围。它可以描述共享规则在本页如何呈现，但不得重新定义角色、字段、状态机、权限、接口结果或跨端验收。

## 6. 需求范围判断

收到需求后先分类：

- **共享规则变化**：角色、权限、术语、字段口径、状态、事实来源、接口语义或跨端流程变化。先改共享文档，再改受影响端。
- **单端页面变化**：仅布局、文案、端内交互或本地状态变化。只改该端页面和 PRD；若明确无共享影响，在 PRD 保留独立声明。
- **跨端功能变化**：一个端的动作会改变另一个端可见内容、权限、状态或结果。必须执行下面的契约先行流程。
- **纯工程变化**：构建、资源路径、性能或内部重构，不改变产品契约。更新 README/QA/技术证据，不伪造产品规则或发布亮点。

不确定属于哪类时，列出可能影响的角色、实体、状态和端，向产品负责人确认；不要根据截图或现有代码猜业务含义。

## 7. 跨端契约先行流程

1. **产品/设计定边界**：确定目标、角色、范围、端职责、业务状态、异常、非本期和跨端验收；开放问题进入决策文档。
2. **后端定事实**：确认数据来源、权限、状态迁移、接口/事件、错误、幂等、并发、审计、同步时效和联调数据。
3. **前端定页面映射**：每个受影响页面引用共享契约，补齐加载、空、输入、校验、提交、成功、失败、权限、返回和刷新行为。
4. **原型 Agent 实现**：只改受影响端的页面、PRD、资产和必要 Canvas 增量；保留其他页面和全部用户画布状态。
5. **团队联调**：用共享联调数据验证主流程、失败、重试、权限、并发和跨端可见性，不以“页面能打开”代替业务验收。
6. **原子交付**：同一 Git diff 包含共享契约、端 PRD、可操作原型、`pendingChanges` 和 QA 证据。
7. **统一发布**：同次产品发布的受影响端使用相同 `product.version` 依次发布；每个发布包快照同一版共享文档。

## 8. 各角色开工入口

| 角色 | 开工前必读 | 需要产出 | 不应做 |
| --- | --- | --- | --- |
| 产品经理 | 01、02、05、90 | 范围、规则、端职责、验收、决策 | 把未决问题写成确定规则 |
| 设计/原型 Agent | 根 README、本端 README、页面 PRD 及其共享契约 | 可操作页面、状态、页面 PRD、必要 Canvas 增量 | 重写共享状态或其他端 Canvas |
| 前端 | 本端 README、02、03、04、目标页面 PRD | 页面状态映射、校验、反馈、恢复和联调结果 | 从截图反推接口或权限 |
| 后端 | 01、02、03、04、05、90 | 数据/状态/权限/接口/幂等/审计契约和联调数据 | 从单端页面文案决定全局规则 |
| 测试 | 02、03、04、05、各端产品验收 | 主流程、异常、权限、并发和跨端一致性证据 | 只检查页面截图或 HTTP 200 |

## 9. 完成定义

跨端功能交付前逐项确认：

- 共享文档无冲突、无未标识的未决项。
- 每个受影响页面 PRD 都有共享契约、本页职责和依赖能力。
- 每个端页面入口、文档、资源、Canvas 节点和关键导航有效。
- 前后端对字段、状态、权限、错误、幂等、同步和审计理解一致。
- 主流程、无数据、失败、重试、越权、并发和跨端刷新均有可判断验收。
- Git diff 没有无关页面、复制的共享规则、临时文件、嵌套仓库或发布包。
- `scripts/protodock-validate <workspace-root>` 通过；新工作区使用 `--workspace-contracts-as-errors` 精准阻断协作契约问题。
- 每个受影响子项目根和最终 ZIP 单独通过校验。
- 本地 Player 与公开 Share 实际点击关键跨页和返回流程。
- 正式发布使用统一产品版本，发布历史只产生一条汇总说明。

## 10. 兼容与迁移

- 没有 `protodock.workspace.json` 的旧项目继续使用全部单项目功能。
- 工作区子项目仍可单独打开，不要求修改原 manifest、Canvas 或发布历史。
- 缺少标准共享文档、README 或契约引用的旧工作区默认只收到警告。
- 不得在打开、校验或发布时自动创建文档、移动目录、合并 Git 或重排 Canvas。
- 迁移前先备份、列出端与仓库、识别共享规则重复、提出目标目录和 Git 历史方案，经用户确认后再执行。
- 迁移在新目录和独立迁移分支完成。记录每个旧端的绝对路径、项目 ID、页面/节点/连线/分组数量、最新发布版本和源快照摘要，禁止在验收前覆写旧端。
- 只复制可继续编辑的真实源、页面、PRD、资产、脚本、测试、当前参考和 QA；排除 `.git`、`node_modules`、缓存、旧 ZIP、`dist`、备份和 `temps`。
- 每个子端仍需独立构建、校验和打开；工作区校验不能替代子端校验，子端校验不能替代最终 ZIP 解压校验。
- 至少用真实浏览器逐页检查 HTTP/资源/脚本/空白/坏图，并实际点击每个端的一条主任务路径。旧 Canvas 坐标和连线默认原样保留，除非用户明确要求重新编排。
- `protodock.local.json` 可按端复制以保留可选飞书 Webhook，但必须保持 Git 忽略、权限收紧且不进入 ZIP、Share、Git diff、日志或最终回复。迁移验收只做配置与消息载荷测试，不自动发送真实群消息。
- 正式交付前确认：旧目录未变化、新目录可从工作区和子端分别打开、Git diff 完整、飞书本地配置可用且未泄漏、三个最终 ZIP 均通过、浏览器回归报告可复跑。

## 11. 常见失败

- 在三个端各复制一份权限矩阵，后来只改其中一份。
- 只在入口页写跨端流程，结果页、失败页和接收端没有更新。
- 前端把页面文案当接口契约，后端把数据库字段直接暴露给产品。
- 每个端使用独立长期分支，无法一次审查完整产品变化。
- 在子端再建 Git 仓库，根工作区 diff 看不到真实改动。
- 把开放问题、系统边界、提示词版本或架构解释显示在用户原型中。
- 发布时多个端使用不同产品版本或不同共享文档快照。
- 只验证工作区或源码目录，没有验证每个最终 ZIP 和公开 Share。
