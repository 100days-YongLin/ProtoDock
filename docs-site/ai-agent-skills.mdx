title: Skill 安装与文件契约
description: 安装 ProtoDock Skill，并让不同 Agent 交付同一种项目结构。
---

Skill 可以理解为给 AI Agent 的项目说明书。它不是给产品经理手动点击的功能，而是一组让 Agent 遵守的工作规则。

ProtoDock 已把可分发版本放在仓库的 `skills/protodock-canvas/SKILL.md`。这份文件是发布源，团队成员不需要使用维护者电脑中的私有 Skill。

## 一键安装

先下载或克隆 ProtoDock 仓库，在仓库根目录执行：

```bash
# 同时安装给 Codex 和 Claude Code（当前用户的所有项目可用）
./scripts/install-protodock-skill.sh both

# 只安装给 Codex
./scripts/install-protodock-skill.sh codex

# 只安装给 Claude Code
./scripts/install-protodock-skill.sh claude
```

脚本会在覆盖旧版本前创建时间戳备份。安装完成后，重新打开 Agent 或新建会话，让工具重新扫描 Skill。

## 更新已有 Skill

先拉取最新版 ProtoDock 仓库，再重新执行安装命令即可覆盖用户级旧版本：

```bash
git pull
./scripts/install-protodock-skill.sh both
```

如果旧原型仓库曾使用项目级 Skill，则要把目标改为该原型目录：

```bash
./scripts/install-protodock-skill.sh both project /path/to/old-prototype-project
```

更新 Skill 只会替换 Agent 规则文件并备份旧规则，不会修改该原型的页面或 `protodock.project.json`。之后是否加入页面组，仍由下面的分组迁移流程决定。

## 安装到项目

团队希望 Skill 跟随某个原型项目一起协作时，可以安装到项目级目录：

```bash
./scripts/install-protodock-skill.sh both project /path/to/prototype-project
```

不同工具对应的位置如下：

| 工具 | 用户级安装 | 项目级安装 |
| --- | --- | --- |
| Codex | `~/.agents/skills/protodock-canvas/SKILL.md` | `<project>/.agents/skills/protodock-canvas/SKILL.md` |
| Claude Code | `~/.claude/skills/protodock-canvas/SKILL.md` | `<project>/.claude/skills/protodock-canvas/SKILL.md` |

这些目录遵循 [Codex Skills 官方说明](https://developers.openai.com/codex/skills/) 和 [Claude Code Skills 官方说明](https://code.claude.com/docs/en/skills)。

<Note>
  用户级适合经常处理多个 ProtoDock 项目的人；项目级适合团队仓库，让进入该项目的 Agent 只在当前项目加载规则。
</Note>

## 手动安装

无法运行 Shell 脚本时，从仓库下载 [`skills/protodock-canvas/SKILL.md`](/skills/protodock-canvas/SKILL.md)，放入上表对应目录即可。目录和文件名必须保持为 `protodock-canvas/SKILL.md`。

Windows PowerShell 安装到 Codex 用户目录的示例：

```powershell
New-Item -ItemType Directory -Force "$HOME/.agents/skills/protodock-canvas"
Copy-Item "skills/protodock-canvas/SKILL.md" "$HOME/.agents/skills/protodock-canvas/SKILL.md"
```

Claude Code 只需把目标中的 `.agents` 改为 `.claude`。

## 验证安装

- Codex：新建任务后说“使用 `protodock-canvas` Skill 检查这个项目的上传包”。
- Claude Code：进入项目后输入 `/protodock-canvas`，或直接要求它使用该 Skill 检查项目。

Agent 能说出 ZIP 根目录必须直接包含 `protodock.project.json`、`pages/` 和 `docs/`，即说明加载的是新版规则。

## 用 Skill 升级旧版原型

旧版原型不需要为了继续打开而升级。`canvas.groups` 是可选字段，没有它时 ProtoDock 会继续显示原来的平铺页面和画布。只有希望按业务模块组织左侧列表时，才需要执行一次分组迁移；列表收起与搜索不会隐藏 Canvas 页面。

先让 Agent 只分析、不修改：

```text
请使用 protodock-canvas Skill 分析当前旧版 ProtoDock 原型，给出 Canvas Groups 分组提案，暂时不要修改文件。
请结合页面文档、页面标题和现有关键连线，列出每个组的名称、主入口、成员页面、未分组页面和不确定项；同时先检查 page、node、edge、entry、doc 是否完整。
```

确认提案后再执行迁移：

```text
请使用 protodock-canvas Skill，按刚才确认的分组提案升级当前旧版原型。
迁移前备份 protodock.project.json；只新增 canvas.groups，不修改 project、pages、nodes、坐标、edges、锚点、notes 和未知字段；不执行自动重排。完成后重新读取 manifest，并对比迁移前后的页面、节点、连线和备注，最后校验 ProtoDock 上传 ZIP。
```

迁移没有把握的页面应继续留在“未分组”，不能根据文件名硬猜。分组完成后如需整理某一组的树形布局，应单独要求“预览该组的局部布局”，确认预览后再应用。

<Warning>
  不要只说“升级旧版原型”。这可能被理解为重建整个 manifest。明确要求“只新增 canvas.groups，不重排画布”，才能保护产品经理已经整理好的节点和连线。
</Warning>

## Skill 解决什么问题

在 ProtoDock 场景里，Skill 会告诉 Agent：

- 这个项目是原型工作台，不是普通页面项目
- 哪些文件可以生成或修改
- 哪些画布状态必须保护
- 页面组、组成员和主入口为什么不能被普通导出重建
- 修改 `protodock.project.json` 前需要备份
- 最终页面必须能被浏览器作为静态入口加载

这样 Codex、Claude Code 或其他 Agent 即使使用不同的实现方式，也能把结果交付成 ProtoDock 可以读取的项目结构。

## 文件契约

每个 ProtoDock 项目至少需要这些文件：

```text
prototype-project/
├── protodock.project.json
├── pages/<page-id>/index.html
└── docs/<page-id>.md
```

`protodock.project.json` 是项目清单。它告诉 ProtoDock 项目有哪些页面、每个页面的入口在哪里，以及画布节点和连线应该如何恢复。

## 最终 ZIP 契约

ProtoDock 上传包是独立交付物，ZIP 根目录必须直接包含：

```text
protodock.project.json
pages/
docs/
assets/（如有）
```

不能在外层再套项目名、版本号、“完整交付包”或“ProtoDock上传包”目录。完整交付包与 ProtoDock 专用上传包必须分别生成，不要让用户拿完整交付包上传 ProtoDock。

Agent 必须重新解压最终 ZIP，并按其中的 manifest 验证每个 `pages.*.entry` 和 `pages.*.doc` 都存在且相对于 ZIP 根目录。只校验打包前的源码目录，不算完成交付。

最终 ZIP 还必须通过 Canvas 完整性检查：每个 page 恰好对应一个 node，所有边的端点存在，不允许重复节点、重复连线、悬空连线或节点重叠。连线交叉、穿过无关节点和间距不足必须作为明确警告返回。

## 跨页导航验收

Agent 必须扫描最终 ZIP 中每个页面的控件和脚本，并输出“来源页面、控件文案、目标 `pageId`、目标入口”的路由表。每个跨页控件都要显式声明 `data-protodock-page`、`protodock:` 链接或导航协议，目标必须存在于 manifest 且只对应一个 Canvas 节点。

以下情况会阻止交付：

- 仅使用 `window.location`、旧 `data-page` 或按钮文案猜测目标
- 使用脱离项目作用域的 `/pages/...` 根路径
- 目标页面未注册、入口或文档缺失、目标节点重复
- 用查询参数切换一个已经单独注册为 manifest 页面的业务状态

ProtoDock 会尽量恢复旧原型的脚本跳转，方便历史文件继续预览；这只是兼容能力，不能替代 Agent 的交付校验。页面状态已经有独立 `pageId` 时，应直接指向该页面，例如“饮奶”应指向饮奶历史状态页，而不是通用 `record?type=milk`。

<Warning>
  `document missing`、`NotFoundError`、所有页面同时无法预览时，优先检查 ZIP 根目录。浏览器扩展产生的报错不应误判为 ProtoDock 页面错误。
</Warning>

## Agent 应该更新什么

Agent 通常可以更新：

- `pages/**`
- `docs/**`
- `assets/**`
- `protodock.project.json` 中的 `project` 和 `pages`

Agent 默认不应该整体重写：

- `canvas.nodes`
- `canvas.edges`
- `canvas.notes`
- `canvas.groups`
- 节点坐标
- 锚点方向
- 未知字段

更完整的字段级规则见 [Agent 写入边界](/agent-boundaries)。

## 为什么要保护 canvas

页面源码是可生成资产，画布排布是产品经理的工作成果。产品经理在 ProtoDock 里拖动节点、连接流程、补充说明后，这些信息会沉淀在 `canvas` 中。

如果 Agent 每次生成页面时都重写 `canvas`，产品经理整理过的流程关系就会丢失。因此普通页面迭代默认只更新页面、文档、素材和必要的页面注册信息。

<Warning>
  只有用户明确说“重排画布”“重建 flow”或“覆盖 canvas”时，Agent 才能重写画布数据。
</Warning>

重排时应先备份 manifest 并生成布局预览；确认后只能修改 `canvas`。普通 build/export 和上传操作都不能自动重排。完整编排规则见 [画布协作](/canvas-workflow)。
