---
title: 多端产品工作区
description: 用一个轻量工作区管理同一产品的多个原型端和共享产品文档。

---

同一个产品包含家长端、教师端、Web 管理端等多个原型时，不需要把它们合并成一个巨型项目。保留每个端原有的完整 ProtoDock 项目，再在外层增加一个产品工作区即可。

## 目录结构

```text
product-workspace/
├── protodock.workspace.json
├── README.md
├── .gitignore
├── shared-docs/
│   ├── 01-product-overview.md
│   ├── 02-roles-and-permissions.md
│   ├── 03-domain-data-contract.md
│   ├── 04-interface-event-contract.md
│   ├── 05-cross-end-flows.md
│   └── 90-decisions-open-questions.md
└── prototypes/
    ├── parent/
    ├── teacher/
    └── admin/
```

每个 `prototypes/<endpoint>/` 仍须直接包含自己的 `protodock.project.json`、`pages/`、`docs/` 和可选 `assets/`，所以它既能从工作区进入，也能像旧项目一样单独打开。

新建独立产品时，以工作区根目录作为产品唯一 Git 根。产品已经位于同一产品 monorepo 时，保留现有上层仓库作为唯一 Git 根，工作区根仍作为 ProtoDock 的产品源码边界。两种情况都不要在子端内再次创建 `.git`，也不要把多个长期独立分支当作不同版本。一次跨端改动应在同一功能分支和同一审查中包含共享契约、各端 PRD、原型与变更记录。

可选的跨端 `references/`、`qa/`、`scripts/` 和 `tests/` 可以放在根目录；`temps/`、`protodock/backups/`、本地密钥、缓存、日志和发布 ZIP 必须忽略。不得在根目录或子端内创建 `dist/`、完整交付副本或第二套可编辑项目。

## 工作区清单

```json
{
  "schemaVersion": 1,
  "product": {
    "id": "youerjia",
    "name": "优儿嘉",
    "description": "幼儿园家园协同产品",
    "version": "v1.2.0"
  },
  "sharedDocs": "shared-docs",
  "projects": [
    { "id": "parent", "name": "家长端", "path": "prototypes/parent" },
    { "id": "teacher", "name": "教师端", "path": "prototypes/teacher" },
    { "id": "admin", "name": "Web 管理端", "path": "prototypes/admin" }
  ]
}
```

所有路径都相对于工作区根目录，不允许使用绝对路径或 `..`。端标识和项目路径不能重复。

## 打开与编辑

点击 **打开本地项目**，选择直接包含 `protodock.workspace.json` 的目录。ProtoDock 会先检查全部子项目，再打开上次使用的端：

- 顶部切换当前端；
- Canvas 始终完整显示当前端的页面、分组和连线；
- 左侧“共享产品文档”打开产品级 Markdown；
- 有未保存修改时，必须先保存才能切换端；
- 普通旧项目没有工作区清单时，界面和行为保持不变。

`shared-docs/` 当前只读取直属 `.md` 文件，并按文件名排序。一级标题会显示为文档名称。适合写产品概述、角色权限、跨端公共业务规则、数据口径和术语；端内页面交互仍写在对应 `docs/<page-id>.md`。

## 共享文档规范

| 文档 | 必须回答 | 开工角色 |
| --- | --- | --- |
| `01-product-overview.md` | 产品目标、用户场景、边界、端职责、成功标准 | 全员 |
| `02-roles-permissions.md` | 角色、权限矩阵、数据范围、越权处理 | 产品、前后端 |
| `03-domain-data-contract.md` | 术语、实体、字段口径、状态机、事实来源、一致性 | 产品、前后端 |
| `04-interface-event-contract.md` | 前后端职责、接口、错误、幂等、审计、联调数据 | 前后端 |
| `05-cross-end-flows.md` | 流程索引、主流程、状态事件、异常补偿、跨端验收 | 全员 |
| `90-decisions-open-questions.md` | 已确认决策、待确认问题、变更记录 | 全员 |

页面 PRD 继续使用页面文档规范，并在开头增加：

```md
## 关联共享契约

- 共享契约：`03-domain-data-contract`、`04-interface-event-contract`、`05-cross-end-flows` 中的 `FLOW-CONTENT-PUBLISH`。
- 本页职责：展示当前用户有权查看的已发布内容。
- 依赖能力：内容列表、权限校验和发布状态查询。
```

引用文件标识和流程标识，不要把状态机、接口或权限表复制进每个页面。没有跨端依赖的页面也应写明 `共享契约：无（端内独立流程）`，让接手者不用猜测遗漏还是有意独立。

## 团队如何开工

### 产品与设计

1. 先读产品概述、角色权限和现有跨端流程。
2. 确定本次变化属于共享规则、单端页面还是跨端流程。
3. 跨端变化先更新共享状态、端职责、异常和端到端验收；未确认内容进入决策文档，不写进原型 UI。
4. 列出受影响端、页面 ID、流程 ID 和非本期范围，再交给实现角色。

### 后端

1. 先读领域数据契约、接口事件契约和目标跨端流程。
2. 明确事实来源、权限校验、状态迁移、请求响应、错误、幂等、并发、审计和联调数据。
3. 不从页面截图反推业务规则；契约缺失或冲突时先回到共享文档确认。
4. 完成后以可观察结果支持页面 PRD 和跨端验收，不把内部实现细节写进用户界面。

### 各端前端与原型 Agent

1. 先读本端 README、目标页面 PRD 及其引用的共享契约。
2. 只实现本端负责的输入、展示、导航、状态和恢复行为。
3. 页面 PRD 写清加载、空、失败、成功、权限和返回行为；共享状态机和接口口径只引用、不复制。
4. 只增量修改受影响页面和 Canvas，保留其他端和现有布局。

## 跨端需求闭环

一个跨端功能只有同时满足以下条件才算完成：

1. 共享文档已确定角色、领域、接口、状态、端职责、异常补偿和跨端验收。
2. 每个受影响页面 PRD 都声明共享契约、本页职责和依赖能力。
3. 前端原型可操作，后端契约可以实现和联调，产品验收具有明确前提、操作和预期。
4. 同一 Git diff 包含共享文档、受影响端页面与 PRD、必要 Canvas 增量和 `pendingChanges`。
5. 工作区、每个受影响子项目和最终发布 ZIP 均通过校验；关键路径在本地 Player 与公开 Share 中实际点击通过。
6. 同一次产品发布影响多个端时，各端使用相同产品版本依次发布，发布快照固化当时的共享文档。

## 完整产品文档

工作区模式下，“完整产品文档”和发布后的公开 Share 产品文档都按以下顺序汇总：

1. 产品封面与当前产品版本；
2. 共享产品文档；
3. 当前端的页面 PRD 与可操作原型。

它不会创建第二套总 PRD、功能数据库、跨端 Canvas 或关系图。共享规则只维护一份，页面规则仍跟着页面走。

## 发布

发布仍以当前端为单位，并显示“当前原型 + 共享产品文档”的范围。ProtoDock 会：

- 在临时 ZIP 的 `docs/_shared/` 中固化共享文档；
- 在发布清单中生成只读 `workspaceSnapshot`；
- 使用 `<产品标识>-<端标识>` 作为公开与 GitHub 发布标识，避免不同端覆盖；
- 使用工作区 `product.version` 作为统一产品版本；
- 成功后把版本写回工作区和当前端正式变更历史。

如果一次产品发布同时修改多个端，依次发布这些端，并填写同一个产品版本号。子项目源目录不会出现 `docs/_shared/` 或 `workspaceSnapshot`。

## 校验

```bash
scripts/protodock-validate /absolute/path/to/product-workspace
```

工作区校验会检查清单、共享文档目录和全部子项目。每个最终发布 ZIP 仍需单独校验，因为最终归档才是交付门槛。

校验还会提示：核心协作文档或章节缺失、页面 PRD 未声明共享契约、子端缺少 README、子端嵌套 Git 仓库。默认提示不影响旧工作区继续打开；新工作区或 CI 使用：

```bash
scripts/protodock-validate /absolute/path/to/product-workspace --workspace-contracts-as-errors
```

## 旧版兼容

- 没有 `protodock.workspace.json` 的单项目仍按原流程打开、编辑、保存、发布和 Share。
- 工作区内任一子项目仍可单独打开，页面、Canvas、文档和历史不需要迁移。
- 旧工作区缺少新版协作文档时只收到升级警告，不会自动改写文件或阻止默认发布。
- 工作区只增加导航、共享文档和发布快照，不合并 Canvas、不改变子项目 manifest、不建立第二套产品数据库。

迁移旧版三端时，必须在新目录和独立迁移分支完成，旧目录保持不变。迁移记录需包含每个旧端的路径、项目 ID、页面/Canvas 数量、最新发布版本和源快照摘要。完成工作区、子端、最终 ZIP 和真实浏览器关键路径验收后，才能把新目录交给团队使用。

每端可继续使用本地 `protodock.local.json` 保存可选飞书机器人配置，但该文件必须被 Git 忽略且排除在 ZIP、Share 和公开文档之外。迁移验收只验证配置和消息载荷，不自动向真实群发送测试消息。

| 原有能力 | 单项目模式 | 工作区模式 |
| --- | --- | --- |
| 本地目录打开与变更检测 | 完整保留 | 当前端复用同一能力 |
| 页面树、搜索、分组和 Canvas | 完整保留 | 当前端完整展示 |
| 页面 PRD 编辑与保存 | 完整保留 | 增加共享文档编辑 |
| 可操作预览、跨页与返回 | 完整保留 | 当前端复用同一 Player |
| 完整产品文档、打印/PDF、全屏演示 | 完整保留 | 增加共享文档和端标识 |
| 截图、复制、设备壳选项 | 完整保留 | 当前端复用同一能力 |
| 公开 Share 与交互预览 | 完整保留 | 增加共享文档快照 |
| GitHub 发布、最新版链接、飞书通知 | 完整保留 | 使用产品端发布标识和统一版本 |
| 变更历史与 `pendingChanges` | 完整保留 | 发布后同步产品版本与当前端历史 |

工作区是单项目能力的外层编排，不是替代实现。任何工作区功能都不得通过删除、绕过或另写一套旧功能来实现。
